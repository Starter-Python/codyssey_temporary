### 1. 기능별 함수 분리 기준과 각 함수의 역할

### 2. 프롬프트 데이터 구조(리스트/딕셔너리)의 필드 구성과 접근 방식
* **자료구조**: `list[Prompt]` (리스트 안에 딕셔너리가 담긴 형태)
* **필드 구성 (`Prompt` TypedDict)**:
  * `title` (`str`): 프롬프트 제목
  * `content` (`str`): 프롬프트 지시문 전체 내용
  * `category` (`str`): 분류 카테고리 ("텍스트 생성", "이미지 생성" 등)
  * `favorite` (`bool`): 즐겨찾기 등록 여부 (`True` / `False`)
* **접근 방식**:
  * **목록 순회**: `for number, prompt in enumerate(prompts, start=1):` 로 O(N) 순회
  * **필드 읽기**: `prompt["title"]`, `prompt["content"]`, `prompt["favorite"]` 키 기반 직접 접근 O(1)
  * **필드 갱신**: `prompt["favorite"] = not prompt["favorite"]` 키 기반 직접 수정 O(1)

### 3. 입력 검증(범위/빈 값) 로직의 위치 및 동작 방식
* **빈 값 검증**: `get_non_empty_input(label)` 함수 내부에서 `while True`를 돌며 `value.strip()`이 빈 문자열인 경우 안내 메시지를 출력하고 유효한 문자열이 들어올 때까지 반복합니다.
* **범위 검증**: `is_valid_prompt_number(value, prompts)`와 `get_prompt_index(prompts)`에서 `value.isdigit()` 검사와 `1 <= int(value) <= len(prompts)` 범위를 확인하여 인덱스 에러(`IndexError`)를 사전 차단합니다.
* **메뉴 번호 검증**: `get_menu_choice()`에서 입력값이 `MENU_OPTIONS` 딕셔너리의 키(`"1"`~`"8"`)에 존재하는지 검사하여 예외 없는 안전한 분기를 보장합니다.

### 4. 커밋을 기능 단위로 나눈 기준
* **Conventional Commits 규격 준수**: 변경의 목적에 따라 접두어(`feat`, `chore`, `docs`, `test`, `refactor`, `merge`)를 명확히 구분했습니다.
* **원자적 커밋(Atomic Commit)**: 한 커밋에 서로 다른 기능을 섞지 않고, "기본 프롬프트 모델 구성", "목록 출력 기능", "검색 및 즐겨찾기 구현", "단위 테스트 작성", "문서화" 등 의미 있는 단위로 분리하여 코드 리뷰 및 이력 추적이 용이하도록 구성했습니다.

## 📌 항목 3. 핵심 기술 원리 적용

### 1. 리스트와 딕셔너리를 선택한 이유 (장단점 비교)
* **리스트(`list`)를 컬렉션으로 선택한 이유**:
  * **장점**: 데이터의 순서(등록 순서)가 보장되고, 1번부터 시작하는 콘솔 메뉴 번호(인덱스 `0` ~ `N-1`)와의 매핑이 직관적입니다.
  * **단점**: 특정 요소를 검색하거나 삭제할 때 O(N) 순회가 필요하지만, 콘솔 관리 프로그램 규모(수십~수백 개)에서는 메모리 오버헤드가 적고 구현이 가장 단순하여 최적입니다.
* **딕셔너리(`dict`)를 단일 프롬프트 객체로 선택한 이유**:
  * **장점**: `title`, `content`, `category`, `favorite`과 같이 서로 다른 타입의 연관 데이터를 키-값(Key-Value) 쌍으로 명확히 표현할 수 있고, 필드 접근 속도가 O(1)로 빠릅니다.
  * **단점**: 고정된 스키마 강제가 없으므로(이를 방지하기 위해 `TypedDict` 사용), 키 이름 오타 위험이 있으나 명시적인 키 네이밍으로 해결했습니다.

### 2. 메뉴 반복에 `while`을 사용한 이유와 반복 종료 조건 설계
* **`while` 루프 사용 이유**:
  * 사용자가 '종료'를 선택하기 전까지 프로그램이 몇 번이나 실행될지 횟수를 미리 알 수 없기 때문에, 조건 기반 무한 루프(`while True`) 구조가 필수적입니다.
* **반복 종료 조건 설계**:
  1. **정상 종료**: 사용자가 메뉴 `8`(종료)을 입력하면 `run_menu_loop()` 내부에서 `return` 또는 `break`가 실행되어 루프를 탈출하고 종료 메시지를 출력합니다.
  2. **비정상/중단 종료**: 사용자가 `Ctrl+C`(KeyboardInterrupt) 또는 입력 스트림 종료(EOFError)를 발생시킬 경우, `read_user_input()`에서 커스텀 예외 `UserInputCancelled`를 발생시켜 `main()`에서 안전하게 캐치 후 프로세스를 정상 종료합니다.

### 3. 검색 기능에서 “제목 또는 내용 포함” 구현 방식
```python
def find_prompts(prompts: list[Prompt], keyword: str) -> list[Prompt]:
    normalized_keyword = keyword.casefold()
    return [
        prompt
        for prompt in prompts
        if normalized_keyword in prompt["title"].casefold()
        or normalized_keyword in prompt["content"].casefold()
    ]
```
* **구현 원리**:
  * 파이썬의 `in` 연산자를 활용하여 부분 문자열(Substring) 포함 여부를 검사합니다.
  * `lower()`보다 유니코드 특수문자 및 다국어 대소문자 처리에 강력한 `casefold()`를 적용하여 영문 대소문자 구분을 없앴습니다.
  * 논리합(`or`) 연산자를 통해 제목 또는 내용 중 하나라도 키워드가 포함되면 리스트 컴프리헨션으로 즉시 필터링합니다.

### 4. 브랜치를 분리해서 작업한 이유와 병합 시점/기준
* **브랜치 분리 이유**:

## 📌 항목 4. 심층 인터뷰

### 1. 프로그램 종료 후 데이터 유지(영속화) 설계 및 파일 형식 선택
* **선택할 파일 형식**: **JSON (`prompts.json`)**
  * **선택 이유**: Python 내장 `json` 모듈을 사용할 수 있어 추가 패키지가 필요 없고, `list[dict]` 데이터 구조를 1:1로 직렬화(Serialization)/역직렬화(Deserialization)하기에 가장 직관적이고 표준적입니다.
* **영속화 아키텍처 설계**:
  1. **시작 시 (`load_prompts`)**: `prompts.json` 파일 존재 여부를 확인하여, 파일이 있으면 로드하고 없거나 손상되었을 경우 `create_initial_prompts()`로 초기화.
  2. **데이터 변경 시 (`save_prompts`)**: 프롬프트 추가, 즐겨찾기 변경, 수정/삭제 발생 시 즉시 `json.dump(prompts, f, ensure_ascii=False, indent=2)`를 호출하여 실시간 동기화.
  3. **원자적 저장 (Atomic Write)**: 저장 도중 프로세스가 비정상 종료되더라도 데이터가 깨지지 않도록 `prompts.json.tmp`에 임시 저장 후 원자적 교체(`os.replace`) 수행.

### 2. 같은 제목의 프롬프트가 생길 때 충돌 처리 규칙
* **현재 구현 규칙**:
  * **제목과 내용이 모두 동일한 경우**: 완전 중복으로 간주하여 `find_duplicate_prompt()`에서 등록을 차단하고 기존 프롬프트가 존재함을 안내.
  * **제목은 같으나 내용이 다른 경우**: 동일 주제의 '다른 버전' 또는 '개선안'일 수 있으므로 등록 허용.
* **확장 시 충돌 해결 규칙**:
  * 각 프롬프트에 `uuid.uuid4()` 기반의 고유 ID(`id`)를 부여하여 식별자를 제목에서 ID로 분리.
  * 사용자가 동일한 제목을 입력했을 때: `[1] 덮어쓰기`, `[2] 새 버전으로 등록(예: 회의록 요약 v2)`, `[3] 취소` 선택 메뉴를 제공.

### 3. 병합 과정에서 충돌(Conflict) 발생 시 해결 순서 (3단계)
1. **1단계: 원인 파악 (Investigate)**
   * `git status` 명령어로 충돌이 발생한 파일 목록(Unmerged paths)을 확인하고, 충돌 파일 내의 충돌 마커(`<<<<<<< HEAD`, `=======`, `>>>>>>> feature-branch`)를 찾아 어떤 변경사항끼리 충돌했는지 코드 맥락을 분석합니다.
2. **2단계: 해결 및 정리 (Resolve)**
